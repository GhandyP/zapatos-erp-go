**Status:** in progress

The provisional slice is one material, one BOM line, one finished variant, and one work order; all manufacturing assumptions remain unvalidated until factory feedback is reconciled.

- Keep the manufacturing and SQLite migration work separate from `openspec/changes/production-readiness-foundations`, whose proposal excludes new business features and storage migration.
- FoxPro integration is outside this initiative unless its scope is explicitly reopened.
- Current storage target: multiple processes on one host with local durable storage, using SQLite with a pure-Go driver for this objective. This does not promise cross-host operation.
- PostgreSQL connection is deferred until after this objective. Keep the current storage boundary portable where practical, then create a separate Markdown plan for the future PostgreSQL integration at objective close.

## SQLite migration design

1. **Transaction boundary:** Each persisted write runs its full domain operation—including reads and validation for stock adjustment or invoice issue—and its audit insert through a context-aware transaction runner/Unit of Work. Commit before returning success; propagate audit/commit errors and roll back both changes.
2. **Storage shape:** Use `database/sql` with a pure-Go SQLite driver. Keep typed repository/domain validation, store serialized business payloads in SQLite, and keep audit events and sessions in tables in the same database. Avoid depending on PostgreSQL now; isolate backend-specific SQL for the later integration.
3. **Strict JSON preflight and source backup:** Before any database write, inspect the five business snapshots (`raw-materials.json`, `finished-goods.json`, `packaging.json`, `logistics.json`, `invoices.json`) and `audit.json`. Missing business files use configured seeds; missing audit means empty; valid `[]` stays empty. Reject whitespace-only, malformed, non-array, unknown-field, trailing-value, duplicate-ID, and invalid-ID inputs. Back up exact bytes and SHA-256 manifest for existing business/audit snapshots and `sessions.json` under `DataDir/migration-backups/json-import-v1`; `bootstrap.json` is configuration, not a snapshot. Use private 0700 directory/0600 files; reuse an existing backup only if every byte and manifest entry matches, otherwise fail. Back up sessions only; never import their tokens.
4. **One-time import and startup gate:** Task 5h holds a host-local advisory lock across a non-mutating marker/store probe, snapshot preparation, backup publication, SQLite schema setup, and import. Probe an existing database read-only before reading JSON: a complete `store_migrations` marker skips stale snapshots; an incomplete marker or nonempty unmarked `store_records` fails closed before snapshot reads. For an absent/eligible DB, preflight and back up exact sources before calling mutating `OpenSQLite`, then call `ImportJSONOnce` with the prepared plan; its transaction rechecks state, reserves the marker as first write, inserts without upsert, verifies counts, marks complete, and commits. Any error rolls back data and marker. The startup lock prevents another same-host instance from completing migration between the probe and snapshot read. Task 5g defines production collection strings and audit ID selection; task 5i wires them.
5. **Audit behavior:** Insert each audit event in the same transaction as its business change. Preserve the current 500-event retention cap for this objective; future retention policy remains a separate decision. FoxPro sync state remains in-memory/out of scope.
6. **Permissions:** Restrict the shared data directory and SQLite database/WAL/SHM files to the application identity. All same-host instances must run under the same UID; verify actual sidecar modes in tests. Keep the migration backup private as noted above.
7. **Backup and rollback:** Quiesce all instances for SQLite file-copy backups and verify restoration before resuming. After the first database write, never roll back by switching to stale JSON; restore from a consistent SQLite backup or fix forward. A completed import backup is preserved, never overwritten by a different source set.
8. **Future PostgreSQL:** Do not add a Postgres driver, endpoint, or deployment now. At objective close, create the requested separate Markdown plan for that later integration.

## Provisional manufacturing MVP

Build one controlled showcase based on existing roadmap assumptions: record an opening quantity for one raw material, define a one-line BOM for one existing finished-product variant, then complete one work order. Completion consumes the required material and adds good output to finished stock in the same SQLite transaction, linked to the order.

- **BOM:** one variant, one raw material, quantity per output unit, unit, and revision.
- **Work order:** `draft → released → completed`, with planned/good quantity, actor, and timestamps.
- **Roles:** administrator configures the BOM; production creates, releases, and completes orders. Add explicit manufacturing permissions rather than relying on general stock-write access.
- **Provisional assumptions:** integer quantities and one unit convention. The current raw-material model has no on-hand balance, and integer consumption may not match factory practice; validate after the prototype works.
- **Acceptance:** successful completion consumes the expected material and increments finished stock exactly once; insufficient stock, invalid references/quantities, duplicate completion, or unauthorized actions produce no partial changes.
- **Non-goals:** routes, multiple BOM lines, lots, scrap/rework, purchasing, packaging/shipping, invoicing, costing, and external integrations.
- **Factory gate:** show the functioning prototype to factory users, record terminology/quantity/state mismatches, and revise before marking the workflow accepted or production-ready.

This is separate from the existing `production-readiness-foundations` OpenSpec change, which explicitly excludes business features and storage migration. Keep the prototype as its own bounded workstream; do not expand that proposal.
